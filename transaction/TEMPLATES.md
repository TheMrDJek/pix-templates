# 🔄 Транзакционные шаблоны PIX RPA

## 📋 Введение

Транзакционные шаблоны в PIX RPA представляют собой решения для автоматизации бизнес-процессов, требующих обработки наборов данных. Эти шаблоны основаны на четырехэтапной модели состояний (Init → GetTransaction → ProcessTransaction → End) и предназначены для обработки множества элементов данных с гарантией целостности.

## ✨ Ключевые особенности

- **4 состояния** машины состояний: Init, GetTransaction, ProcessTransaction, End
- **Обработка множества элементов** данных последовательно или параллельно
- **Восстановление после сбоев** с продолжением с точки отказа
- **Изоляция транзакций** для обеспечения надежности обработки
- **Гибкая система уведомлений** через различные каналы

## 📂 Доступные шаблоны

| Шаблон | Описание |
|--------|----------|

## 📱 Типы уведомлений

Все представленные шаблоны по умолчанию имеют суффикс EAU (Exchange для Admin и User), но доступны и другие варианты:

| Суффикс | Описание |
|---------|----------|
| **EA** | Exchange для Admin - уведомления через почтовый сервер Exchange только для администраторов |
| **EU** | Exchange для User - уведомления через почтовый сервер Exchange только для пользователей |
| **EAU** | Exchange для Admin и User - уведомления через почтовый сервер Exchange для администраторов и пользователей |
| **S** | SMTP - уведомления через стандартный почтовый протокол SMTP |
| **SA** | SMTP для Admin - уведомления через SMTP только для администраторов |
| **SU** | SMTP для User - уведомления через SMTP только для пользователей |
| **SAU** | SMTP для Admin и User - уведомления через SMTP для администраторов и пользователей |

## 🚀 Выбор подходящего шаблона

### По источнику данных
- **RQ/Q2Q** - когда данные хранятся в очередях оркестратора
- **F/F2Q/Q2F** - когда данные находятся в файлах или нужно сохранять результаты в файлы
- **M/M2Q** - когда данные поступают по электронной почте
- **LT/LT2Q** - когда данные представлены в виде объектов в памяти
- **R/R2Q** - когда данные хранятся в табличном формате
- **DB/DB2Q** - когда данные хранятся в реляционной базе данных
- **K** - когда используется брокер сообщений Kafka
- **RMQ** - когда используется брокер сообщений RabbitMQ

### По типу автомата
- **SM** - базовый автомат для простых сценариев без особых требований к надежности
- **SMR** - шаблон с механизмом повторов для повышения надежности
- **SMRUI** - шаблон с поддержкой взаимодействия с пользовательским интерфейсом приложений

### По типу оповещения
- Выберите подходящий суффикс в зависимости от того, кто должен получать уведомления (администраторы, пользователи или обе группы) и какой тип почтового сервера вы используете (Exchange или SMTP).

## 🔄 Конфигурация шаблонов

### Управление ассетами по окружениям

Транзакционные шаблоны поддерживают динамическое переключение между окружениями разработки, тестирования и промышленной эксплуатации через входной параметр `Environment`.

Если параметр `Environment` заполнен, робот ищет в мастере (оркестраторе) ассеты с соответствующим суффиксом окружения:
- `_dev` - ассеты для среды разработки
- `_test` - ассеты для тестовой среды
- `_prod` - ассеты для промышленной среды

Если параметр `Environment` оставлен пустым, робот использует ассеты без суффиксов.

> 💡 **Рекомендация:** Используйте стандартизированные суффиксы `_dev`, `_test` и `_prod` для всех ассетов, требующих разных значений в различных окружениях. Храните в ассетах с суффиксами все параметры, которые различаются между средами: URL-адреса, пути к файлам, учетные данные и т.д. Если не требуется использование суффиксов, оставьте параметр Environment пустым.

### Формат конфигурации

Конфигурация в шаблонах хранится в формате `Dictionary<string, string>`, так как оркестратор (мастер) возвращает значения ассетов только в виде строк. При необходимости использования других типов данных выполняется преобразование типов в коде.

### Работа с учетными записями

Для работы с учетными данными (логины, пароли) в шаблонах используется особый подход:
1. В конфигурации хранится только название ассета с учетной записью
2. При необходимости использования учетной записи применяется скрипт `GetCredentials`
3. Скрипт возвращает объект, содержащий логин и пароль

Такой подход обеспечивает:
- Безопасное хранение учетных данных в зашифрованном виде в оркестраторе
- Отсутствие паролей в коде или конфигурационных файлах
- Централизованное управление учетными данными
- Возможность изменения учетных данных без изменения кода робота
